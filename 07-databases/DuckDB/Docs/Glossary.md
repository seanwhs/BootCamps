# Glossary of Terms: Embedded Analytics & DuckDB Engineering

---

## A

* **Apache Arrow:** An independent, language-agnostic in-memory columnar data format that standardizes memory layouts across programming languages, enabling zero-copy memory sharing between tools like Pandas, PyArrow, and DuckDB.
* **Apache Parquet:** A compressed, efficient columnar storage file format optimized for analytical query performance and lakehouse architectures.
* **Asynchronous Execution:** A programming model that allows non-blocking operations, enabling the system to continue processing other tasks while waiting for I/O or external responses to complete.

## C

* **Client-Server Architecture:** A traditional database model (such as PostgreSQL, MySQL, or SQL Server) where the database runs as an independent daemon process and clients communicate with it over network sockets or TCP/IP connections.
* **Columnar Storage (OLAP):** A storage architecture that stores data column by column contiguously on disk and in memory, drastically reducing disk I/O and memory bandwidth for analytical queries.
* **Concurrency:** The ability of a system to execute multiple tasks or queries overlappingly, managed in DuckDB through multi-threaded query execution schedulers.

## E

* **Embedded Database:** A database engine (such as SQLite or DuckDB) that operates entirely within the host application's process space as a linked library, eliminating network overhead, daemons, and server configuration.
* **Execution Plan (Physical Plan):** The tree of physical operators (such as sequential scans, hash joins, and aggregations) generated by the database optimizer to execute a SQL query.

## L

* **Lakehouse Architecture:** A modern data management paradigm that combines the low-cost object storage of data lakes with the ACID transactions, partitioning, and schema governance of data warehouses.
* **List / Array (Nested Type):** A data type supporting ordered sequences of elements within a single table column, allowing multi-valued attributes to be stored without relational join tables.

## O

* **OLAP (Online Analytical Processing):** Query workloads characterized by heavy read-heavy aggregations, multi-dimensional grouping, window calculations, and complex analytics over large volumes of historical data.
* **OLTP (Online Transaction Processing):** Transactional workloads characterized by high-concurrency, isolated row-level inserts, updates, deletes, and fast primary-key lookups.
* **Out-of-Core Processing:** An execution strategy where an engine processes datasets larger than physical system RAM by dynamically spilling intermediate states to temporary disk storage.

## P

* **Partition Pruning:** An optimization technique where the query engine evaluates filters against directory and file metadata to skip entire unmatching partition paths on disk.
* **Partitioning:** Organizing data into hierarchical folder structures based on high-cardinality dimensions (e.g., date, region) to optimize storage and query filtering.

## R

* **Row-Oriented Storage (OLTP):** A storage architecture that stores data row by row contiguously on disk, optimized for transactional inserts and single-record retrievals.

## S

* **Struct (Nested Type):** A composite data type containing a fixed collection of named fields, mimicking JSON objects or dictionary structures directly inside a relational column.

## V

* **Vectorized Execution:** A query execution model where the database processes data in contiguous chunks (vectors) rather than individual scalar rows, maximizing CPU L1/L2 cache efficiency and enabling SIMD optimization.
* **Von Neumann Bottleneck:** The performance limitation caused by the speed disparity between fast CPU instruction processing and slower main memory (RAM) data fetching.

## W

* **Window Function:** An analytical SQL construct that computes an aggregate or ranking across a defined row partition while preserving the original row granularity.
* **Work-Stealing Scheduler:** A multi-threading task scheduling mechanism where idle CPU threads dynamically pull execution tasks from busy threads to maximize core utilization.

## Z

* **Zero-Copy Memory Sharing:** An architectural mechanism where a database engine reads memory buffers allocated by another runtime (such as Pandas) in place without duplicating or serializing the data.
