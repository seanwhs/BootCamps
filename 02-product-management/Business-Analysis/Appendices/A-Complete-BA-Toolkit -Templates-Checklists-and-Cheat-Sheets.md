### A.3.1 Interview Guide Template

```
INTERVIEW GUIDE

INTERVIEWEE: [Name]
TITLE/ROLE: [Title]
DATE/TIME: [Date, Time]
INTERVIEWER: [BA Name]
OBJECTIVE: [What we need to learn]

WARM-UP QUESTIONS (5 min):
1. "Tell me about your role and how long you've been here."
2. "What does a typical day look like for you?"
3. "What do you enjoy most about your work?"

CORE QUESTIONS (30-40 min):
4. "What are the biggest challenges you face in your role?"
5. "What tools/systems do you use daily?"
6. "What frustrates you most about the current systems/processes?"
7. "What workarounds have you developed to get things done?"
8. "What information do you need that you don't currently have?"
9. "If you could change one thing about your work, what would it be?"
10. "How do you currently handle [specific process/task]?"
11. "What does an ideal solution look like to you?"
12. "What would help you be more effective?"

DEEPER PROBES (10-15 min):
13. "Can you tell me more about that?"
14. "Can you give me a specific example?"
15. "What makes that particularly challenging?"
16. "What do you mean by [term]?"
17. "How did you handle that situation?"

CLOSING (5-10 min):
18. "Is there anything I haven't asked that you think is important?"
19. "Who else should we talk to?"
20. "Would you be open to a follow-up conversation if needed?"

POST-INTERVIEW NOTES:
- Key Insights:
- Pain Points Identified:
- Requirements Implied:
- Follow-up Questions:
- Additional Stakeholders Suggested:
```

## Appendix A.4: Business Process Modeling Cheat Sheets

### A.4.1 BPMN 2.0 Quick Reference

**FLOW OBJECTS:**

| Element | Symbol | Description |
|---------|--------|-------------|
| Activity | Rectangle with rounded corners | Work performed in the process |
| Event | Circle | Something that happens |
| Gateway | Diamond | Decision point |
| Pool | Large rectangle | Participant in the process |
| Lane | Within pool | Role within a participant |

**EVENT TYPES:**

| Event | Symbol | Description |
|-------|--------|-------------|
| Start Event | Thin circle with no fill | Begins the process |
| End Event | Thin circle with thick border | Ends the process |
| Intermediate Event | Double circle | Occurs between start and end |
| Timer Event | Clock icon | Triggered by time |
| Message Event | Envelope icon | Sending or receiving a message |
| Error Event | Lightning bolt icon | Handling an error |

**GATEWAY TYPES:**

| Gateway | Symbol | Description |
|---------|--------|-------------|
| Exclusive (XOR) | Diamond with X | Only one path is taken |
| Inclusive (OR) | Diamond with circle | One or more paths are taken |
| Parallel (AND) | Diamond with plus | All paths are taken simultaneously |
| Event-Based | Diamond with circle | Choice based on events |

**CONNECTING OBJECTS:**

| Element | Symbol | Description |
|---------|--------|-------------|
| Sequence Flow | Solid line with arrow | Flow of the process |
| Message Flow | Dashed line with arrow | Communication between pools |
| Association | Dotted line | Artifact linking |

### A.4.2 Process Analysis Checklist

```
PROCESS ANALYSIS CHECKLIST

PROCESS NAME: [Process Name]
DATE: [Date]
ANALYST: [Name]

1. PROCESS IDENTIFICATION
   [ ] Process name is clear and descriptive
   [ ] Process owner is identified
   [ ] Process boundaries are defined (start and end)
   [ ] Process stakeholders are identified

2. PROCESS DOCUMENTATION
   [ ] Process is documented in BPMN or similar notation
   [ ] All activities are included
   [ ] Decisions (gateways) are identified
   [ ] Events are identified
   [ ] Swimlanes show clear ownership

3. PROCESS MEASUREMENT
   [ ] Inputs are identified
   [ ] Outputs are identified
   [ ] Metrics are defined
   [ ] Baseline measurements exist
   [ ] Targets are defined

4. PROCESS ANALYSIS
   [ ] Value-added vs. non-value-added identified
   [ ] Bottlenecks identified
   [ ] Waste identified
   [ ] Improvement opportunities documented
   [ ] Automation opportunities identified

5. PROCESS IMPROVEMENT
   [ ] To-Be process is documented
   [ ] Improvements are quantified
   [ ] Implementation plan exists
   [ ] Success metrics defined

6. STAKEHOLDER VALIDATION
   [ ] As-Is process validated with stakeholders
   [ ] To-Be process validated with stakeholders
   [ ] Stakeholder feedback incorporated
   [ ] Approval obtained
```

## Appendix A.5: Requirements Quality Checklists

### A.5.1 Requirements Quality Criteria (Q.U.A.L.I.T.Y.)

```
REQUIREMENTS QUALITY CHECKLIST

Requirement ID: [ID]
Requirement Description: [Description]

Q - QUESTIONABLE ASSUMPTIONS
[ ] Are the requirements based on solid evidence?
[ ] Have we validated assumptions with stakeholders?
[ ] Are there any unstated assumptions?

U - UNAMBIGUOUS
[ ] Is it clear what the requirement means?
[ ] Could different people interpret it differently?
[ ] Is the language precise and clear?
[ ] Are technical terms defined?

A - ATOMIC
[ ] Does the requirement capture one specific need?
[ ] Can it be developed and tested independently?
[ ] Is it the right size for a single requirement?

L - LEGIBLE
[ ] Is it easy to read and understand?
[ ] Is it well-structured?
[ ] Is it free from unnecessary jargon?
[ ] Is it written in active voice?

I - INDEPENDENT
[ ] Is it testable on its own?
[ ] Does it have clear acceptance criteria?
[ ] Is it free from dependencies on other requirements?

T - TRACEABLE
[ ] Can it be traced to a business need?
[ ] Can it be traced to stakeholders?
[ ] Can it be traced to solution elements?
[ ] Is there a clear source?

Y - YOURS (STAKEHOLDERS' NEEDS)
[ ] Does it truly represent what stakeholders need?
[ ] Have we validated with stakeholders?
[ ] Is the stakeholder perspective represented?

EVALUATION RESULT: [Pass / Needs Revision / Fail]
REVISION NEEDED: [Describe what needs to change]
```

### A.5.2 INVEST User Story Checklist

```
USER STORY INVEST CHECKLIST

Story: [Story Description]

I - INDEPENDENT
[ ] Is the story independent of other stories?
[ ] Can it be developed in any order?
[ ] Are dependencies identified and managed?

N - NEGOTIABLE
[ ] Is there room to discuss the details?
[ ] Can the team and product owner negotiate the implementation?
[ ] Is it written as a placeholder for conversation?

V - VALUABLE
[ ] Does it deliver value to the user or business?
[ ] Is the value clear and measurable?
[ ] Would the user care if this story wasn't delivered?

E - ESTIMABLE
[ ] Can the team estimate the effort?
[ ] Is it clear enough to estimate?
[ ] Does the team have the necessary knowledge?

S - SMALL
[ ] Is the story small enough for one sprint?
[ ] Is it sized appropriately (3-8 story points)?
[ ] Does it fit within the team's capacity?

T - TESTABLE
[ ] Are acceptance criteria clear?
[ ] Can it be tested with objective pass/fail criteria?
[ ] Are testing scenarios identified?

RESULT: [Ready / Needs Work]
COMMENTS: [What needs to be improved]
```

### A.8.2 Definition of Ready Checklist

```
DEFINITION OF READY (DoR)

A user story is ready when:

[ ] Written in "As a... I want... So that..." format
[ ] Acceptance criteria are defined and clear
[ ] Sized appropriately (fits in one sprint)
[ ] Dependencies are identified and resolved
[ ] The team understands the story
[ ] Estimated (story points or size)
[ ] Prioritized (priority is known)
[ ] Stakeholders are available for clarification
[ ] Independent of other stories (where possible)
[ ] Testable
```

### A.8.3 Definition of Done Checklist

```
DEFINITION OF DONE (DoD)

A user story is done when:

[ ] Code is written
[ ] Code is reviewed (peer review)
[ ] Unit tests are written and pass
[ ] Integration tests pass
[ ] Acceptance criteria are met
[ ] User acceptance testing (UAT) is complete
[ ] Documentation is updated
[ ] Code is deployed to staging environment
[ ] No critical or high priority defects remain
[ ] Stakeholder accepts the story
[ ] Showback/demo is provided
[ ] Sign-off is obtained
```

### A.8.4 Story Splitting Techniques

```
STORY SPLITTING TECHNIQUES

1. BY USER ROLE
   - Break stories by different user types
   - Example: Patient scheduling vs. Admin scheduling

2. BY USE CASE
   - Split by different scenarios
   - Example: Book, cancel, reschedule

3. BY PRIORITY
   - Must have vs. nice to have
   - Example: Core booking vs. reminders

4. BY WORKFLOW
   - Split by process steps
   - Example: Search, select, confirm, verify

5. BY COMPLEXITY
   - Simple vs. complex scenarios
   - Example: Online booking vs. complex multi-provider scheduling

6. BY DATA
   - Split by different data types or sources
   - Example: Patient data vs. provider data

7. BY UI/UX
   - Split by screens or interactions
   - Example: Search screen vs. confirmation screen

8. BY FEATURE
   - Split by features within an epic
   - Example: Patient scheduling vs. provider scheduling

SPLITTING CHECKLIST:
[ ] Stories are independent
[ ] Stories deliver value independently
[ ] Stories are estimable
[ ] Stories are testable
[ ] Stories are the right size (3-8 points)
```

### A.9.2 Normalization Reference

```
NORMALIZATION REFERENCE

1NF (First Normal Form):
- No repeating groups
- Each cell has a single value
- Each record is unique

Example:
BEFORE: PatientID, PatientName, Phone1, Phone2, Phone3
AFTER: PatientID, PatientName, PhoneNumber (one record per phone)

2NF (Second Normal Form):
- Must be in 1NF
- No partial dependencies
- All attributes depend on entire primary key

Example:
BEFORE: OrderID, ProductID, Quantity, ProductName, ProductPrice
AFTER: Order (OrderID), Product (ProductID, ProductName, ProductPrice), OrderLine (OrderID, ProductID, Quantity)

3NF (Third Normal Form):
- Must be in 2NF
- No transitive dependencies
- No non-key attribute depends on another non-key attribute

Example:
BEFORE: EmployeeID, DepartmentID, DepartmentName, DepartmentLocation
AFTER: Employee (EmployeeID, DepartmentID), Department (DepartmentID, DepartmentName, DepartmentLocation)
```

## Appendix A.16: Glossary of BA Terms

```
GLOSSARY OF BA TERMS

Acceptance Criteria: Conditions that must be met for a user story or requirement to be accepted.

Agile: Iterative approach to software development emphasizing flexibility, collaboration, and customer feedback.

As-Is: Current state of a process or system.

ATDD (Acceptance Test-Driven Development): Practice where acceptance tests are written before development begins.

BA (Business Analyst): Professional who bridges business needs and technology solutions.

BABOK: Business Analysis Body of Knowledge - global standard for BA.

BDD (Behavior-Driven Development): Practice of specifying system behavior in plain language.

BPMN: Business Process Model and Notation - standard for process modeling.

BRD (Business Requirements Document): Document defining business needs and requirements.

Business Capability: An organization's ability to achieve a specific outcome.

Business Case: Justification for a project including costs, benefits, and ROI.

Capability Mapping: Process of documenting an organization's capabilities.

CBA (Cost-Benefit Analysis): Financial analysis comparing costs and benefits.

CRUD: Create, Read, Update, Delete - common data operations.

Data Dictionary: Repository of information about data elements.

Data Flow Diagram (DFD): Diagram showing data movement through a system.

Definition of Done (DoD): Criteria for a user story to be considered complete.

Definition of Ready (DoR): Criteria for a user story to be ready for a sprint.

Dependency: Relationship where one requirement depends on another.

Elicitation: Process of gathering requirements from stakeholders.

Entity: A thing of interest in a system (e.g., Patient, Appointment).

Entity Relationship Diagram (ERD): Diagram showing entities and their relationships.

Epic: Large user story broken down into smaller stories.

Feasibility Study: Assessment of whether a solution is viable.

Gap Analysis: Comparison of current state to future state.

Gateway: Decision point in a process model.

INVEST: Criteria for good user stories (Independent, Negotiable, Valuable, Estimable, Small, Testable).

KPI (Key Performance Indicator): Measurable value showing goal achievement.

Metadata: Data about data.

MoSCoW: Prioritization technique (Must, Should, Could, Won't).

Non-Functional Requirement: Quality attribute of a system (performance, security, etc.).

Normalization: Process of organizing data to reduce redundancy.

OKR (Objectives and Key Results): Goal-setting framework.

PESTLE: External analysis framework (Political, Economic, Social, Technological, Legal, Environmental).

Pool: A participant in a BPMN process.

Persona: Detailed profile of a stakeholder archetype.

PoC (Proof of Concept): Small implementation to test feasibility.

Power-Interest Matrix: Tool for prioritizing stakeholder engagement.

Product Backlog: Prioritized list of work in Agile.

RACI: Responsibility matrix (Responsible, Accountable, Consulted, Informed).

Reference Data: Data defining permissible values.

Requirements Traceability Matrix (RTM): Linking requirements to tests and implementation.

ROI (Return on Investment): Measure of financial return.

Root Cause Analysis: Identifying underlying causes of problems.

RTM (Requirements Traceability Matrix): Document linking requirements.

SIPOC: High-level process mapping (Suppliers, Inputs, Process, Outputs, Customers).

Story Mapping: Visual exercise organizing user activities and tasks.

SWOT: Analysis framework (Strengths, Weaknesses, Opportunities, Threats).

To-Be: Future state of a process or system.

Transition Requirements: Requirements for moving from current to future state.

UAT (User Acceptance Testing): Testing by end users.

User Journey Map: Visual representation of a user's experience.

User Story: Short description of functionality from a user's perspective.

Value Stream Mapping: Process of identifying waste and value in processes.

Verification: Checking that requirements are built correctly.

Validation: Checking that the right solution was built.

WBS (Work Breakdown Structure): Breakdown of project work.

Wireframe: Low-fidelity representation of a user interface.

XOR (Exclusive OR): Gateway where only one path is taken.
```
